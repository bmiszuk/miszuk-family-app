# Application boundaries

One React application, one Cloudflare Worker, and one D1 database remain the deployment unit.

Status reviewed September 30, 2026 at application release `4d3b89c`: architecture refactor and Users & Permissions through Phase 4 are complete; family push enrollment and Birthday/Chat categories are deployed. Family Polls V1 is added in the October 1 release described below. See [Roadmap](docs/ROADMAP.md) for remaining acceptance checks and future work. No further refactor is required before feature development.

- `src/app`: shell, current-user loading and existing hash navigation.
- `src/features`: feature pages and their Home cards. Home composes these cards; groceries owns Quick Add, calendar owns its summary, chat owns the pinned message, and Directory owns family dates.
- `src/shared`: browser HTTP/hooks and shared UI. Polling and mounted-page behavior are intentionally unchanged.
- `src/domain`: pure, browser/server-safe date, display and Directory relationship rules. No React, database or credentials here.
- `src/api/shared/auth.js`: Cloudflare JWT validation and origin protection, called by the Worker before routing.
- `src/api/shared/accounts.js` and `accountGate.js`: verified Cloudflare identity to an active provisioned account, active Directory person, and optional active household. The Worker awaits this boundary before every API handler, including legacy routes and cached Cozi responses. Approved identities bind atomically on first use. Directory email and default-household fallback are not authorization inputs. `identity.js` retains only legacy comparison support and the protected household constant.
- `src/api/shared/permissions.js`: feature-specific policy decisions and household query scope. Unknown actions deny. Explicit Administrator actions govern household assignment/management, relationship creation/removal, and profile/anniversary corrections. Unknown actions and unrelated feature privileges remain denied.
- `src/api/admin/handler.js`: Administrator-only account roster/detail and bounded security-audit display. Responses explicitly serialize display fields; no raw identity/audit records. Directory exposes these through an Administrator disclosure and per-person access information. `mutations.js` implements pending-Member provisioning, enable/disable, role changes and replacement of another account’s approved email, with transaction-time authority/revision guards and atomic audits. Last usable Administrator protection applies; self-identity changes require operator recovery. All successful first-use bindings increment the account revision.
- `src/api/<feature>`: validation, feature authorization calls and persistence configuration. Shared `records.js` retains the existing versioned CRUD mechanics; it contains no feature-name branches. It is optional plumbing, not a framework future features must use.
- `src/index.css`: ordered stylesheet entrypoint. Most existing rules remain in `shared/base.css`; Calendar rules establish feature CSS ownership without rewriting the cascade.

## Development and technical-health principles

- **GitHub is the authoritative project documentation.** Record accepted decisions, requirements, implementation status and operating procedures in this repository; chat history and private working notes are not the only record. Keep secrets and private backup data outside Git, documenting only approved storage/recovery locations. The [roadmap](docs/ROADMAP.md) tracks status and debt; feature documents hold detail.
- **Design major modules before implementation.** Establish purpose, bounded initial scope, data ownership, authorization, dependencies, navigation, testing and recovery approach before building. Resolve consequential open decisions with Bob; implement in small independently verifiable releases. A roadmap idea is not implementation approval.
- **Review technical health after roughly 2–4 meaningful feature projects.** Use this as a checkpoint, not a count of commits or minor fixes. Review feature boundaries, authorization consistency, data/migration integrity, testing, dependencies, operational burden and documentation. Review sooner when a concrete risk emerges. Record findings and justified follow-ups in the existing roadmap; a review does not automatically authorize refactoring.
- **Require a concrete reason for infrastructure.** Reuse the existing stack unless an approved feature has a demonstrated need for another service, datastore, queue or abstraction. Weigh maintenance, cost, security, backup and recovery responsibilities before adding it; do not build infrastructure for hypothetical scale.
- **Watch feature sprawl.** Keep each project bounded, preserve clear feature ownership and usable navigation, and avoid turning related ideas into unrequested dependencies. Revisit overlap and ongoing maintenance cost before expanding the portal. Keep optional ideas deferred until explicitly selected.
- **Maintain successor and recovery documentation with changes.** A technically competent family member should be able to understand and recover the system without Bob or AI chat history. Update relevant runbooks, backup/restore verification, rollback constraints and credential-recovery references when behavior or operations change. Use the [handbook outline](docs/infrastructure/HANDBOOK_OUTLINE.md) to track missing operational knowledge, without recording secrets.

## Existing policy compatibility

Directory profile editing permits self, parent-to-child and spouses in both directions, plus an explicit Administrator edit-any override. Eligible Members can edit anniversaries, but household assignments and relationship creation/removal are Administrator-only, including nested person saves and creation payloads. Household creation/rename/retirement is Administrator-only; names remain readable by Members. Privileged mutations recheck active Administrator authority and insert security audit records in the same D1 transaction; failures roll back all changes. Household edits require the expected current name for concurrency protection. Chat ownership and household SQL scopes are unchanged. Accounts without an active household receive no Grocery/Dinner access. Account-linked people cannot be deleted; legacy login email remains frozen.

The Worker remains the authentication and application-account boundary for family-wide reads, person creation, Cozi and legacy endpoints. Record validity/consistency rules remain local: Dinner assignees must belong to the household, Directory relationship transactions and D1 constraints remain authoritative, and default/occupied households cannot be retired. These are not automatically inherited as Vehicle authorization rules.

## Legacy API inventory

`/api/people`, `/api/families`, and `/api/events` remain routed and unchanged. No current frontend caller was found in the repository. Local events have existing API regression tests; families/people now have explicit compatibility tests. This repository inspection cannot establish whether an external client uses them, so none is removed. Current Calendar uses `/api/cozi-calendar`.

## Deliberately deferred

Invitations, Chat moderation, cross-household Grocery/Dinner administration and Photos remain deferred. Vehicles has the core feature described below; attachments remain deferred. Current account roles/status are authoritative at the request boundary; revocation must not be implemented by deleting Directory people. Household query scope must accompany any future cross-household permission expansion; changing a UI button or a single boolean alone is insufficient.

Vehicles defines its own ownership/actions explicitly. Further splitting `domain/familyDisplay.js`, feature CSS extraction and coordinating duplicate polling can proceed separately when useful; none is required to add a feature handler. The legacy endpoints must be included in any future system-wide access/revocation rollout.

## Vehicles Phase 1 — core API and UI

Migration `0012_vehicles.sql` adds vehicle specifications and versioned maintenance records with household/person/account references; no existing table is changed. Chunk 2 requires no further migration. `src/domain/vehicles.js` validates fields, the optional fixed category list and mileage behavior. `src/api/vehicles/service.js` owns household-scoped reads and transactional writes. `handler.js` exposes bounded, sanitized `/api/vehicles` routes behind the central account gate; payloads cannot choose an ordinary Member's household or authenticated author. Driver options are scoped to the authorized household. Responses omit internal account attribution and authentication identifiers.

`src/features/vehicles` owns the compact list, maintenance history, specifications and forms, reached through `#vehicles` in the account menu only. Vehicle labels and last-known mileage share one row; specifications use a disclosure. Sold/Inactive replaces vehicle deletion. Optional Category and editable Performed by are distinct from persisted authenticated create/update metadata. Maintenance changes refresh vehicle revisions; stale writes surface conflicts. Explicit administration mode uses a household selector and the feature-specific policies below. No R2, attachments, Home card, notification category or later-phase features are implemented.

Shared policy names ordinary household actions explicitly. `vehicle.readAny` and `vehicle.correctAny` are separate Administrator actions, requested through deliberate administration mode and rechecked against live account/identity state in SQL. Cross-household corrections and manual mileage corrections write an audit in the same transaction. Administrator authority does not bypass driver validity, optimistic concurrency or other data constraints. Maintenance updates/deletion retain authenticated attribution and never lower last-known mileage. See [Vehicles requirements](docs/VEHICLES_REQUIREMENTS.md) for field conventions and the next integration boundary.

## Household Polls V1

`src/api/polls` and `src/features/polls` own single-question/single-choice household polls. Migration 0011 adds polls/options/recipient snapshots/responses and preserves existing notification claims while admitting the polls category. The account gate applies to every route; SQL additionally requires active current household membership and the creation-time recipient snapshot. Administrator and family relationships grant no exception. Atomic creation derives recipients server-side; votes recheck scope/open state/option/revision at the write. Expiration is creation + seven days in UTC, displayed in Chicago time, with no new scheduler. Creator-only early close and paginated history share the same boundary. Home has a bounded summary; `#polls` is secondary navigation. See [Polls requirements](docs/POLLS_REQUIREMENTS.md).

## Notifications — family enrollment, Birthdays, Chat and Polls

`src/api/notifications` owns authenticated account-only configuration, subscriptions, preferences and the test sender. The central account gate and origin checks apply to every route. Members and Administrators have identical own-device rights; there is no send-as or cross-account subscription access. Migration `0009_push_notifications.sql` adds `push_subscriptions` and `notification_preferences`, plus an identity-replacement trigger that invalidates devices in the same transaction as replacement.

`src/features/notifications` owns the settings destination and explicit sign-out cleanup. `public/sw.js` handles only notification display and safe Home/Chat click routing. It has no fetch handler, cache, offline family data, background API requests or authentication bypass. Navigation through a notification still encounters the normal Access/account boundary.

Following the successful physical-iPhone pilot, Phase 1C enables voluntary per-device enrollment and manual self-tests for all eligible active provisioned accounts using `NOTIFICATIONS_AUDIENCE=active_accounts`. The central account gate plus enrollment/send-time SQL checks remain authoritative; neither household nor Administrator role grants an exception. Both kill switches remain mandatory, and an optional exact-ID restriction supports pilot rollback. A stable VAPID private key is held only in the Worker secret and the operator-confirmed Bitwarden recovery record. Birthdays, Family Chat and new household Polls are the only automatic categories; permission prompts still require explicit user action. See [Notifications operations](docs/NOTIFICATIONS.md) for privacy, recovery and rollout status.

`notifications/events.js` owns internal birthday, committed-Chat and committed-Poll dispatch. UTC Cron runs at 13:00 and 14:00 with an America/Chicago 08:00 guard; birthday calculations reuse Home rules. Chat and Poll dispatch use post-commit `waitUntil` and never control publication success. Poll sends exclude the creator and recheck snapshot/current household and unanswered/open state at claim and send time. Poll lock-screen content is generic; tap opens Home. Migration `0010_notification_deliveries.sql` supplies atomic event/account claims for at-most-once delivery. Account-wide category preferences are separate from device enrollment, default birthdays/chat/polls on, and preserve explicit opt-outs. Category sends reuse eligibility/lifecycle checks immediately before provider dispatch. See notification operating notes for delivery limits and schedule rollback.
